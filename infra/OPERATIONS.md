## Updating the website with new code (the most common task)

Workflow:

1. Make changes locally on `phase4-docker` (or whatever branch you're working on).
2. `git commit` and `git push origin phase4-docker`.
3. From your laptop, run this one-liner:

```powershell
ssh ubuntu@35.223.220.115 'cd /opt/app && sudo git fetch origin && sudo git reset --hard origin/phase4-docker && sudo docker compose -f docker-compose.prod.yml --env-file .env.production -p app up -d --build && sudo docker image prune -f'
```

What it does:

| Step | Effect |
|---|---|
| `git fetch origin` | Pulls down the new commit metadata. |
| `git reset --hard origin/phase4-docker` | Makes the VM's working tree match the branch exactly. Safe because the VM never edits files locally. |
| `docker compose ... up -d --build` | Rebuilds only the Docker layers that changed (layer cache), recreates only the containers whose image hash changed. The `db` container and its `pgdata` volume are not touched → **your Postgres data survives every deploy**. |
| `docker image prune -f` | Reclaims the disk space from now-dangling old images. |

**Speed expectations:**

| Type of change | Rebuild time |
|---|---|
| Controller / model / view only (no gem changes) | ~30 sec |
| Tailwind / asset changes | 1 – 2 min |
| Adding or upgrading a gem | 5 – 15 min (slow because of swap) |
| First build from scratch (no cache) | 25 – 35 min |

### If your change includes a DB migration

Append a migration step to the deploy command:

```powershell
ssh ubuntu@35.223.220.115 'cd /opt/app && sudo git fetch origin && sudo git reset --hard origin/phase4-docker && sudo docker compose -f docker-compose.prod.yml --env-file .env.production -p app up -d --build && sudo docker compose -f docker-compose.prod.yml --env-file .env.production -p app exec -T web bin/rails db:migrate && sudo docker image prune -f'
```

### After merging `phase4-docker` → `main`

Switch the VM to track `main` once and never think about it again:

```powershell
ssh ubuntu@35.223.220.115 'cd /opt/app && sudo git fetch origin && sudo git checkout main && sudo git reset --hard origin/main'
```

Then update the deploy one-liner above to use `origin/main` instead of `origin/phase4-docker`.

## Common operational commands

All examples assume you SSH'd in (`ssh ubuntu@35.223.220.115`).

### See container state

```bash
sudo docker ps -a
sudo docker compose -f /opt/app/docker-compose.prod.yml -p app ps
```

### Tail the Rails log

```bash
sudo docker compose -f /opt/app/docker-compose.prod.yml -p app logs -f web
```

(Add `--tail 200` to start with the last 200 lines instead of from the beginning.)

### Tail the Postgres log

```bash
sudo docker compose -f /opt/app/docker-compose.prod.yml -p app logs -f db
```

### Open a Rails console on the running app

```bash
sudo docker compose -f /opt/app/docker-compose.prod.yml --env-file /opt/app/.env.production -p app exec web bin/rails console
```

### Run a one-off migration manually

```bash
sudo docker compose -f /opt/app/docker-compose.prod.yml --env-file /opt/app/.env.production -p app exec web bin/rails db:migrate
```

### Restart just the web container (no rebuild)

```bash
sudo docker compose -f /opt/app/docker-compose.prod.yml --env-file /opt/app/.env.production -p app restart web
```

### Stop everything (without losing data)

```bash
sudo docker compose -f /opt/app/docker-compose.prod.yml --env-file /opt/app/.env.production -p app down
```

### Start everything back up (no rebuild)

```bash
sudo docker compose -f /opt/app/docker-compose.prod.yml --env-file /opt/app/.env.production -p app up -d
```

### Wipe the database (DESTROYS DATA — use only intentionally)

```bash
sudo docker compose -f /opt/app/docker-compose.prod.yml --env-file /opt/app/.env.production -p app down -v
# then re-deploy to recreate fresh + seed
```

### Postgres shell

```bash
sudo docker compose -f /opt/app/docker-compose.prod.yml --env-file /opt/app/.env.production -p app exec db psql -U stackonomics -d stackonomics_production
```

### Back up the database to a SQL file

```bash
sudo docker compose -f /opt/app/docker-compose.prod.yml --env-file /opt/app/.env.production -p app exec -T db \
  pg_dump -U stackonomics stackonomics_production \
  > ~/stackonomics-backup-$(date +%Y%m%d-%H%M).sql
```

Then `scp` it down to your laptop:

```powershell
scp ubuntu@35.223.220.115:~/stackonomics-backup-*.sql .
```

## Disk and memory health

The VM is small. Check on it every once in a while.

```bash
df -h /          # disk usage  - get worried above 80%
free -m          # memory usage - normal idle is ~250-400 MB used
sudo docker system df  # how much disk Docker is holding
```

If Docker is hoarding disk:

```bash
sudo docker image prune -f       # safe - removes dangling images
sudo docker builder prune -f     # removes build cache (next build is slower)
sudo docker system prune -af     # nuclear - removes EVERYTHING not in use
```

## DNS

Currently `ruby.desk-buddy.cloud` is set up in Porkbun as a **URL forward**,
which sends an HTTP 302 redirect to `http://35.223.220.115/`. The browser
then ends up displaying the IP in the address bar.

To keep the hostname visible in the URL bar, change Porkbun to a real
A record:

1. In Porkbun DNS for `desk-buddy.cloud`:
   - **Delete** the existing URL-forward record for `ruby`.
   - **Add** an `A` record: host `ruby`, type `A`, answer `35.223.220.115`, TTL `600`.
2. Propagation usually takes <1 minute on Porkbun.
3. Verify: `nslookup ruby.desk-buddy.cloud` should return `35.223.220.115`
   directly (not a Porkbun forwarding IP).

## Troubleshooting

### "Connection refused" or hanging SSH right after a deploy

The VM has only 1 GB of RAM. During a heavy build (especially `bundle install`
or `assets:precompile`), it can swap-thrash badly enough that `sshd` is
slow to respond. Wait 2–3 minutes after starting a build before SSH'ing
in a second time, or watch the build over the GCP serial console:

```powershell
cd infra/terraform-gcp
powershell -ExecutionPolicy Bypass -File .\serial-tail.ps1 -Lines 60
```

### The site returns 502 or fails to respond

Check container status:

```bash
sudo docker ps -a
sudo docker compose -f /opt/app/docker-compose.prod.yml -p app logs --tail 100 web
```

Almost every failure mode shows up in the Rails log. If `web` is restarting
in a loop, the log will show why.

### The VM gets into a totally wedged state

Hard-reset it (virtual power cycle — keeps the disk, just reboots):

```powershell
cd infra/terraform-gcp
powershell -ExecutionPolicy Bypass -File .\reset-vm.ps1
```

After ~60 seconds it'll be back. Docker Compose has `restart: unless-stopped`
on both services, so the app comes up automatically after a reboot.

### Need to start completely over from scratch

Recreate the VM (preserves nothing on the box, but the code is in GitHub
and Terraform state knows the rest):

```powershell
cd infra/terraform-gcp
terraform destroy           # ~30 sec
terraform apply -auto-approve   # ~5 min until VM is up, ~30 min until app is live
```

Note: the IP will change. Update `35.223.220.115` references in this file
and in your Porkbun DNS afterwards.

## Where the secrets came from

`.env.production` on the VM contains two random values that cloud-init
generated on first boot:

```
SECRET_KEY_BASE=<128 hex characters from `openssl rand -hex 64`>
POSTGRES_PASSWORD=<32 hex characters from `openssl rand -hex 16`>
```

These values are unique to this specific VM. If you destroy and re-create
the instance, cloud-init generates fresh secrets — which means anything
encrypted with the old `SECRET_KEY_BASE` (signed cookies, Active Storage
URLs, etc.) becomes unreadable. Users will be silently logged out, but
nothing else breaks. The Postgres database starts empty so the new
password is fine.

If you ever need to read the current secrets (e.g. to connect from a
local tool):

```bash
sudo cat /opt/app/.env.production
```

## Tearing it all down

When you're done with the class project and want $0 of ongoing footprint:

```powershell
cd infra/terraform-gcp
terraform destroy
```

That deletes the VM, the disk, the firewall rules, and the VPC. Your
GCP project still exists (free, no resources). To delete the project
entirely, do it in the GCP console: IAM & Admin → Manage Resources →
select project → Delete.

The OCI Terraform module in `infra/terraform/` was never used (we couldn't
get free-tier ARM capacity in us-phoenix-1). It is kept in the repo as a
backup option in case GCP changes the Always-Free terms; running
`terraform destroy` in that folder is a no-op since nothing was ever applied.
